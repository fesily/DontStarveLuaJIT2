- Fixed: **`network.stats` stopped resolving on the Linux 762172 build** (`linux_signatures_{client,server}` and `linux_signatures_cache_*` were red with `network.stats.update_net_stats is missing`). In the new build `cNetworkClientObject2::UpdateNetStats` fetches the network client at `[rakpeer+278h]`, shrinks the frame from `140h` to `110h`, forms the ring slot address with `LEA (%base,%idx,8)` and performs the accumulation as `MOV tmp,[ptr]; ADD tmp,reg; MOV [ptr],tmp` instead of an in-place `ADD [ptr],reg`. The Linux pattern in `NetStatsSignatures` was rewritten against the new body (exactly one hit in each binary), and `decode_net_stats` rule 4 now accepts both the LEA form and the register round-trip (the old in-place ADD shape still passes). The ring/accumulator candidates also gained a "the most recent writer of this register must be this `[this+disp]` load" guard — without it the GUID's `[this+1a0h]` load is claimed by the later indexed LEA and the decoder reports `ringPtrOff=0x1a0`. The LEA form additionally requires the computed slot address to be dereferenced as `[dst+0..7]`, and the register round-trip requires each link of load → arithmetic → store-back to consume the previous one, with the store base still originating from the same pointer load; one regression fixture each proves that unrelated scaled arithmetic on the GUID (`lea r10,[r11+r11*8]`) and a load/clobber/re-point/store sequence are rejected (with the loose matching restored they report `ringPtrOff=0x1a0` and no layout at all, respectively). Both Linux binaries decode to `listingOff=0x1c0 ringPtrOff=0x318 indexOff=0x328 window=60 stride=8`.

- Changed: **`net_stats_decode` is registered on every platform, not only Windows.** The fixtures and both shapes are host-independent, and Linux never built this unit test before, so the decoder had no teeth there. New `linux_register_ring_form` (LEA + register round-trip positive), `guid_scaled_lea_is_not_the_ring` and `stale_round_trip_is_rejected` (two negatives) fixtures pin the new matching, while the in-place ADD fixtures keep passing.

- Fixed **the Windows client/dedicated server no longer handing the engine's execution-error slots to the swapped-in VM** (`luaSetExecutionErrorSignature` stopped matching): the win64 binaries of build 26474873 rewrote the engine's inlined `lua_setexecutionerror` equivalent (the same change Linux got in 759671) — `strncpy(block, msg, 0x1000)` became an inlined `strlen` plus the CRT's checked `memcpy` (bound `cmp reg,0x1000`, UTF-8 trailing-byte fallback to `0xfff`), a NULL message now goes through a read-only empty-string fallback, and the prologue is no longer `mov rdx,rcx`. - Changed: the installers now **overwrite** the marker instead of deleting it. - Workshop layout is now "published name != loaded name": `tools/update_workshop_tags.py --push-content` stages every module the game maps under `<name>.pkg` (`Injector.dll.pkg`, `deps/*.dll.pkg`, `plugins/<stem>/<stem>.dll.pkg`), and the runtime materializes the canonical name from it immediately before `LoadLibrary` (`core/PackagedModule.hpp`; entry points: shell `InjectorBootstrap` for module resolve + `deps/`, `DynamicPluginLoader` for package candidates, `CoreVmBootstrap` for `plugin_core_vm`). Concurrent boots are safe too: each process stages into its own `*.ds_materialize_tmp_<pid>_<n>` and publishes with a single atomic replace (Windows `MoveFileEx(REPLACE_EXISTING)`, POSIX `rename`), so the loser of the race exits cleanly and a canonical already mapped by a peer stays untouched; a twin caught mid-rewrite by an item update is re-read and PE-section-checked, never published half-written. `update_pending` moves and `plugin.manager` installs use the same atomic replace and no longer fall back to in-place truncation (measured: 6 processes x 400 concurrent materialize + `LoadLibrary`, zero failures).

- On Windows, `lua51DS`/`lua51DS_gengc` can publish LuaJIT trace symbols through the Microsoft-JScript ETW provider (`57277741-3638-4a4b-bdba-0ac6e45da56c`) - no manifest install, no JIT PDB. The publisher is **off by default at runtime** and switched process-wide from Lua with `require("jit.profile").etw(true|false)` (query with `etw()`): `etw(true)` also flushes that VM's traces (equivalent to `jit.flush`, so every live trace ends up with a record and no stale identity survives) and `etw(false)` reports MethodUnload/SourceUnload/ScriptContextUnload at once and stops publishing, with the records freed by their owning VM instead of another thread. **A game or host must therefore call `etw(true)` in the injected VM** (the integration tests and `--hold-for-profile` do), otherwise the ETL carries no JIT names. Once on: every committed trace publishes one source and one method record, so `CPU Usage (Sampled)` in WPA/PerfView resolves a sampled PC inside `[T->mcode, T->mcode + T->szmcode)` to `LuaJIT::TRACE_<traceno>::<chunk>:<startline>`. `tests/performance/cpu.wprp` subscribes it with keyword `0x3` (runtime load/unload plus the start rundown), so attaching to a process that already compiled traces still resolves them, and its event collector buffers were raised because the GUID is shared with every Chakra host on the machine (Edge/WebView2 emit tens of thousands of their own JIT events). Publishing never holds the symbol-cache lock across an `EventWrite` (the lock only covers list/flag updates: ~0.2 us per committed trace, ~15 ns per record), and the worker is joined outside the lifecycle lock with a 5 s timeout diagnostic, so a backpressured session cannot stall trace compilation or VM create/close. `--jit-diagnostics`/`analyze.py` remain a separate stdout/`jit.attach` path, not an ETW symbol consumer. - Fixed `dump_lua_mods` producing only the tail of encrypted-mod sources (hercules / MyxlHttps family, e.g. workshop-3014076942): their loader feeds the decrypted source to the reader in ~8-byte slices **inside a single `lua_load`** (e.g. `myxl_date.lua` 245 slices = 1960 bytes, `speech_moyuxuanli.lua` 43k slices = 344112 bytes) and **re-enters `lua_load` while that reader is still draining**; the shared `thread_local LuaReaderWrapper` was cleared by those re-entrant calls, so every accumulated slice but the last was dropped and the dump held a few trailing bytes. Each `lua_load` now gets its own wrapper (re-entrant calls build and dump their own), so the whole file is assembled into one write: the files above now dump as complete plaintext sources (344112 / 70920 / 36360 / 1960 bytes). The write policy is also three-state now: slices of a stream are appended, a payload at least as large as the dump replaces it (a complete chunk), and stray small payloads after a complete dump are skipped (the complete 80154-byte modmain is no longer clobbered by the 652-slice re-stream that follows it). Dumps are written in binary mode (text mode turned `\n` into `\r\n`, so dumps did not match the real source).

- Tooling/tests: `game_mod_throw_abort` now matches the current game's mod-load failure behaviour - after a modmain error the engine no longer exits; it disables the mod (`Disabling <mod> because it had an error.`) and keeps starting/retrying. The test still requires the `[ds_harness] THROW_ABORT` print (force-enable reached the fixture), the nil-index error text, and the error being handled (disable line, or the engine-VM `Error loading main.lua`), but no longer requires the process to exit; `DedicatedProc.wait_exit` is removed with it.
