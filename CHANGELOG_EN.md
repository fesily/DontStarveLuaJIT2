# Changelog

## Unreleased

- Fixed **the mod not being found (and the game only showing "the luajit mod is not installed") when it is installed into `mods/Luajit` as the README says**: `kModFolderAliases` only listed the all-lowercase `luajit`/`luajit2` plus `DontStarveLuaJit2`/`DontStarveLuaJIT2`, while step 1 of both READMEs used `Luajit` as the example folder name. Windows is case-insensitive and got away with it; Linux/macOS never matched, and the boot log only said `resolve: FAILED (env/marker/scan)` with no hint that the name was one case letter off. `Luajit`, `Luajit2` and `dontstarveluajit2` are now aliases (so old docs/installs keep working; the array size is deduced via `std::to_array` instead of a hand-written count) and both READMEs use `DontStarveLuaJit2` in their examples, with the alias list matching the 9 names in code.

- Fixed **instant crash on startup whenever LuaJIT is enabled** (`SIGSEGV`/`signal 11`: the `call rax` in `lua_gc` jumping to a non-canonical address such as `0x56415741fa1e0ff3`): the C function `lj_gc_fullgc_external` exported by `plugin_debug_profiler` collided with a **data symbol of the same name** in LuaJIT (`LUA_DATA_API void (*lj_gc_fullgc_external)(lua_State*, void*)`, `luajit/src/lj_api.c:1383`). `liblua51DS.so` exports that variable with default visibility, so its own reference goes through a **preemptible GOT entry** (`R_X86_64_GLOB_DAT`); once the profiler module is in the global scope (`RTLD_GLOBAL`, loaded before the VM is mapped), that lookup binds to its **function code address**. `lua_gc` then loads the GOT (code address), dereferences it as a function pointer (reading the function's first 8 bytes, `f3 0f 1e fa 41 57 41 56`) and `call`s it — a guaranteed crash. core.vm's forwarder written into the real variable was never read (`init_luajit_io`'s `*ptr = &forwarder` succeeded but nobody saw it), which presented as "shell and module installed, but JIT always dies". The callback is renamed to `ds_profiler_lj_gc_fullgc_cb`; the service key stays `"lj_gc_fullgc_external"` (`request_service` looks it up by string). On the VM side every host-patchable data symbol of this kind (`lj_gc_fullgc_external`, the 11 IO hooks, `lj_need_transform_path`, `lj_os_date_strftime`, `lua_newproxy` and `extern_error_message_buffer`/`extern_had_execution_error` — 17 in total) is now `visibility("protected")` on ELF (the `luajit` submodule's `LUA_DATA_API`): still in `.dynsym` so `gum_module_find_export_by_name` can address and patch the slot, but the VM's own references no longer go through a preemptible GOT (zero dynamic relocations naming them), which makes "a same-named function hijacks the data variable" independent of load order (the 11 same-named IO functions exported by `plugin_core_vm` are now harmless dead exports too). Reproduced with the real artifacts by replaying the production order (`dlopen(profiler, RTLD_GLOBAL)` → `dlopen(plugin_core_vm)` → libInjector's constructor maps the VM): `lua_gc(L, LUA_GCCOLLECT)` faults with `rip=liblua51DS+0x6915d` and `rax=0x56415741fa1e0ff3`, matching the report; after the rename the GOT binds back to the VM's own variable, `lua_gc` returns normally and the forwarder path still resolves the service by key; with the protected visibility a deliberately built global module exporting all 13 colliding names as functions changes nothing — `luaL_loadfile` / `lua_gc(COLLECT)` run normally and a forwarder written into the slot is still called.

- Fixed **replacing a `<name>.pkg` did not update the DLL it feeds** (two independent causes). First, `ds::packaged::exists_or_materialize` returned early whenever the canonical file already existed and **never compared the twin**, and that helper is the entry point for the shell resolving `Injector.dll`, `DynamicPluginLoader`'s package candidates and `CoreVmBootstrap`'s `plugin_core_vm` — only `deps/` went through `materialize_directory`'s stamp-based refresh, so a manually or Steam-replaced `.pkg` was ignored until the same-named `.dll` was deleted first. Every entry point now calls `materialize` (a no-op without a twin; with one, a single size + PE-stamp comparison; a canonical mapped by another process is still kept, with a log line). Second, `image_stamp` read `TimeDateStamp` without seeking: straight after the `PE\0\0` signature those 4 bytes are the COFF header's `Machine|NumberOfSections<<16`, i.e. constant for a given layout — **a same-size rebuild was classified as the same build** and a replaced `.pkg` refreshed nothing. It now reads the real build stamp at `lfanew + 8` (`SizeOfImage`'s offset is unchanged). Both regression tests fail on the old code: `packaged_module` gains `exists_or_materialize_refreshes_stale_canonical` and `pe_time_stamp_detects_same_size_rebuild` (the test binary's own PE, stamp patched, size unchanged), and `plugin_dynamic_loader` / `injector_bootstrap` each gain a "stale canonical + replaced twin" case.

- Added a **process-wide log level switch**, `log_level` (`InjectorConfig::log_level`, via the existing `ENV_OR_CMD_OPT_VALUE` machinery): environment `log_level=info` or a launcher argument `-log_level=info` / `--log_level info`, values `trace|debug|info|warn|err|critical|off` (plus the `warning`/`error` aliases). Defaults are unchanged — release=`err`, Debug=`trace`, debugger attached=`debug` — and an explicit value wins. `spdlog::set_level` covers every registered logger, so the signature-scan detail in `FunctionRelocation.log` follows the same switch. `spdlog::level::from_str` maps unknown names to `off`, so the value is validated: an unknown level logs `[error] unknown log_level=...` and keeps the default instead of silently muting the log. The `DontStarveInjector_{client,server}.log` sink also stopped truncating — `basic_file_sink(filename, true)` wiped the file on every launch, so a user's failure evidence was erased by the next (possibly successful) start. Measured with the real client injection (`plugin_client_inject_smoke`) twice under `log_level=info`: `bin64/DontStarveInjector_client.log` accumulated 464 lines (183 info lines per run), starting with `[warning] log level set to 'info' by log_level=info` and `[info] Inject start: isClient=true debuggerAttached=0`, and the marker lines of both runs (16:42 / 16:44) survived, proving the append behaviour.

- The `create` build target is now **`create_signatures`**, pairing it with the existing `update_signatures` instead of leaving a bare verb that reads like a directory or an unrelated custom command. All three per-platform `add_custom_target` definitions (macOS / Linux / Windows) are renamed; their commands are unchanged (`signature_updater create`, i.e. the `SIGNATURE_TOOL_MODE=create` tool mode and the `create` CLI argument keep their names). No script, CI workflow or pre-push hook invoked it as `--target create`.

- **Signature DBs now carry a `format_version` and one section per `<system>-<arch>`**: `Mod/signatures_{client,server}.json` is `{"format_version": 2, "platforms": {"windows-x64": {"version": …, "funcs": {…}}, "linux-x64": {…}}}` — Windows, Linux and macOS DBs (including several architectures of one system) coexist in a single file instead of excluding each other; a write replaces only this build's section and leaves the other platform sections untouched. Reads validate `format_version`, the `platforms` structure and this build's section: a different layout version (including the old flat `{version, funcs}` document without the field), a missing own section, a section without integer `version` or non-empty `funcs`, an entry without `offset`/`pattern`, a zero `offset` or invalid JSON all make the DB unusable — and in `update` mode that now **regenerates everything from scratch** instead of failing (only a completely absent file still errors). Writes go through `SignatureJson` only (`tools/Creater/verify_linux_signatures.cpp` no longer hand-builds the JSON); `tests/signatures/run.py` gained stale-`format_version` and missing-own-section cases (requiring the `linux-x64` section to survive each rewrite); the new `signature_json_format` unit test covers read validation, cross-platform merging and idempotent writes; `tests/performance/analyze.py` and `tools/Signature.py` select sections by `<system>-<arch>` too.

- Fixed the **signature-regeneration failure that closed the progress window, killed the process and left no dump**. A generation failure raising `update_signatures_exception` went through `showError` → `MessageBoxA(NULL, …, 0)` (no owner, not TOPMOST, hidden behind the game window) + `std::exit(1)`, and the Windows branch of `showError` wrote **no log line at all** (release builds run at `err` while every phase log is `info`), so all a user saw was "bar stuck at 0% → window gone → process exited". Anything that was not an `update_signatures_exception` (`std::bad_alloc` and friends — one target peaks at ≈954 MB working set during `signature_updater create`) unwound straight out of the progress window's timer callback into `std::terminate`/`abort`: same no-log, no-dump outcome. Changes: both `showError` copies (injector and `plugin_core_vm`) now persist the message with `spdlog::error("fatal: …")`, flush, and show it with `MB_SETFOREGROUND | MB_TOPMOST | MB_ICONERROR`; `update_signatures_from_disasm` gained `catch (const std::exception&)` / `catch (...)` so an unexpected throw becomes that same reported failure instead of terminating the process; `ShowProgressWindow` destroys the window through a RAII guard and resets `progress_ctx` (no zombie window while the error box is up); `SignatureJson::update_signatures` checks the stream and logs a write failure (an unwritable mod dir used to "succeed" and regenerate on every launch); and the progress label now shows `Analyze lua51.dll and game module...` / `Analyze game module (nucleus)...` / `Scan function features...` before phases 1–3 (≈11 s per target locally), repainting synchronously via `UpdateWindow` so a working run no longer looks frozen. Re-ran `windows_signatures` + `windows_signatures_cache`: 104 entries per target, all 208 offsets preserved across create→update.

- Fixed **every Lua plugin silently going dark** (typical symptom: changing `TargetRenderFPS` still yields 60 fps and the log only shows `plugin system disabled: package discovery failed: userdata: 0x…`). Both causes sit in package discovery. First, `GameInjector.DS_LUAJIT_list_plugin_packages` returned a `std::vector<std::string>` directly and sol2 pushes that as a container **userdata**, so `Mod/plugins/init.lua`'s `type(...) ~= "table"` check failed and the whole registry came back empty — it now returns a real 1-based sequence table via `sol::as_table`. Second, `MODROOT` is an engine path, not a disk path (a Workshop item loads from `steamapps/workshop/content/322330/<id>` while `MODROOT` stays `../mods/workshop-<id>/`), so listing it found 0 packages — new `ds::plugin::list_installed_plugin_packages` lists the given directory when it exists and otherwise falls back to `default_plugin_search_dirs()` (the roots the native loader scans: `modmain_path` from `luajit_config.json` plus Workshop discovery). Measured on an offline client with the Workshop item: `discovered 8 package(s)`, `plugin=fps.render status=Loaded`, `Reset fps by SetNetbookMode 60`; `test_plugin_path` gained a case for the engine-relative path fallback.

- **Removed the `ForceDisableTailCall` option** and its VM-side support: the LuaJIT side drops the `jit.disabletailcall` binding together with the `LUA_COMPAT_DYNAMIC_DISABLE_TAILCALL` macro, the `global_State::parser_disable_tailcall` field and the parser's runtime branch (source-tree `jit/vmdef.lua` regenerated accordingly). Lua 5.1 tail-call frames come from the compile-time `LUA_COMPAT_TAILCALL_CFRAME` unconditionally, so the switch had no purpose left; `jit.tailcall` is now only the encrypted-mod detector, and `jit.runtime` drops the matching `jit_force_off` guard. Leftover config keys, if any, are ignored as unknown.

- Encrypted-mod detection is now **always on** and disables JIT directly: the `AutoDetectEncryptedMod` option is gone, `jit.tailcall` uses `options = { always = true }` (gated only by `has_luajit`) and always publishes `ctx.encrypted_mod_manager`. The `jit.runtime` `kleiloadlua` hook now treats a detected encrypted mod like a blacklisted one — every chunk it loads gets `jit.off(chunk, true)` (`PROTO_NOJIT`), the same path as `ModBlackList` — and mods declaring `luajit_compatible` are removed from that set. Also fixed the hook's dependency on the global `jit` (nil after `HideGlobalJIT`) by capturing `ctx.jit` at install time, and it no longer requires `injector` to be present (only the decrypt path needs it). The cache file version moves to `/1.1.0` so caches without `EncryptedMods` are rebuilt.

- Removed the **dead slow-tail-call callback chain**: `lua_ds_set_slowtailcall_cb` was deleted on the LuaJIT side in `0188ec4f` ("Remove load-time tailcall wrapper injection") along with `ParserTailWrapper`, yet the injector still resolved it via `gum_module_find_export_by_name` (always NULL), leaving `luajit_ds_check_slowtailcall` and `registry["LJ_DS_slowtailcall_mods"]` as code with no reader — the `SlowTailCall` / `AnyModDisableTailCall` options only ever wrote names into a table nobody looked at. Also deleted: the injector-side export lookup, the checker function, `ApplySlowTailCall` in the `jit.tailcall` plugin, both modinfo options, and two orphan tests asserting the old wrapper behaviour (`tests/backtrace.lua`, `tests/tailcall_helper_recursion.lua`). Lua 5.1 tail-call frame semantics were already unconditional through the compile-time `LUA_COMPAT_TAILCALL_CFRAME` (on by default for `LJ_DS` + x64/GC64).

- Tests / pre-push hook: added the Windows **full + incremental signature generation** gate (`windows_signatures` / `windows_signatures_cache`). Only Linux had equivalent coverage (`linux_signatures_*` maps the ELF and runs `resolve_lua_signatures_from_modules`, with `--check-cache` covering the incremental update); on Windows the suite only had algorithm-fragment tests (`unique_signature`, `memory_signature_abi`, `xref_pattern`, `graph_seed`) while `create` / `update_signatures` stayed manual custom targets, so DB-format, create-vs-update wiring and cache-repair regressions could pass the hook. The new gate drives the real `signature_updater` tool: `create` rebuilds both client and server DBs from scratch (104 entries each on 759671), then `update` re-resolves them and requires every offset to stay identical; `--check-cache` first corrupts the cached `lua_gettop` pattern into a single nibble (guaranteed ambiguous) and requires update to replace it in place without moving the offset. DBs are written to the new `SIGNATURE_TOOL_OUTPUT_DIR` scratch directory and never to `Mod/signatures_*.json` (the runner also diffs their mtime/size as a backstop). Also fixed a Debug-only crash: `pe-parse` ships as a DLL whose `std::string` layout differs across the CRT ABI, so a Debug consumer that hit the Release `Mod/deps/pe-parse.dll` on PATH read section names through a mismatched `std::string` and died with 0xC0000005 inside `IterSec`; `signature_updater` and `signature_checker` now copy `$<TARGET_RUNTIME_DLLS>` per configuration in POST_BUILD (replacing the frida-gum-only copy rule). Measured: ~6m16s per test in Debug, ~26s in RelWithDebInfo; registered only when the game binaries are present (`GAME_DIR` client+server exe, `version.txt`, `Mod/deps/lua51.dll`), so CI keeps skipping it.

- Tests / pre-push hook: `plugin_client_inject_smoke`, `plugin_client_host_smoke` and `plugin_dedicated_sim_pause` no longer hardcode cluster port 10999; they pick a free UDP port with `tests/harness/ports.py::free_udp_port()` right before writing `server.ini` (a leftover dedicated server, or the user's own server, made the game fail with `RakNet UDP startup failed: SOCKET_PORT_ALREADY_IN_USE` and then trip the engine assert `Illegal termination of worker thread` (0xC0000409) while shutting down - which reads as "the pre-push test script crashed"). `test_nucleus_adapter` drops the hardcoded `lua_getstack` span budget (`< 0x120`), which only matched one particular `lua51.dll` build and broke whenever the reference DLL was rebuilt; it now asserts the structural invariant that the span must not cross the next exported RVA, and prints the reference DLL path/size for triage.

- Signature-DB rebuild (`signature_updater create`) is now 341 s -> ~11 s with **identical output** (104 entries per client/server build; patterns and offsets unchanged). The `scan_by_short_body` mid-body needle search used to scan the full train+target `.text` for every candidate (`lua_setupvalue`/`lua_resume`/`luaL_ref` alone accounted for 192 s); each module now builds one 8-byte window hash (unique/multiple) plus a 4-byte postings index, so a needle is resolved by lookup + fixed-length `memcmp`. `FunctionTable::span_containing` walked back from `upper_bound` to the table head (~4e5 spans) and now returns at the first span that still reaches the address (laminar nesting semantics unchanged - pdata `compared/mismatches` stay identical); `FunctionTable::add`'s sorted insert-per-span became a bulk `assign` (both Nucleus CFG and remap feed ~4e5 spans); `find_function` consults `address_functions` first; the pdata cross-check went from O(spans x ranges) to sort-by-start + prefix-max-end backwards search. The tool must be built **Release** (Debug `nucleus_disasm` 26.8 s vs Release 3.3 s, now the dominant cost). The tool also disables CRT assert/WER dialogs, routes asserts to stderr and makes stdout/stderr unbuffered so a batch run cannot hang on a modal box (`init_ctx` already owns the `FunctionRelocation` logger; `DS_FR_LOG=1` mirrors it to the console). The Linux run surfaced one latent UB that this struct change exposed: `ModuleSections`' `GumMemoryRange` members (`text/pdata/rodata/plt/got_plt/bss/ehframe`) were uninitialized, so `in_plt()/in_got_plt()` read stack garbage when a section was absent; they are value-initialized now (0..0) and `tests/function_relocation/test_xref_pattern` passes again on Ubuntu 24.04 Release.

- Fixed "unravel/weave does nothing" with LuaJIT enabled: the client's item-server call-stack guard formats the whole Lua stack of `BarterLoseItem`/`BarterGainItem`/... frame by frame and byte-compares it against a hardcoded expected trace; on mismatch the client locally fabricates `{"Error":"true","ErrorCode":"E_BALANCE_MISMATCH"}` (the UI only shows "Failed to contact Klei Servers"). The engine-private chunkname helper (Windows `0x140483B20` / Linux `0x4AC6D0`, Ghidra name `lua51::luaGetFuncChunkName`) walks the embedded Lua 5.1 object layout (tag@+8=6, isC@+0xA=0, Proto@+0x20, chunkname@+0x78+0x18), which does not exist under LuaJIT: it returns NULL for every Lua frame, the trace renders `[**untrusted** ...]`, and the guard always fails. Both are custom Lua APIs in the existing replace pipeline: the `src/lua51` reference build exports `lua_setfuncchunkname` / `lua_getfuncchunkname` (the latter mirrors the engine helper by reading `Proto.chunkname`; NULL for C closures/unmarked protos), `LuaApi.hpp` gains both entries (`ctx->api._lua_setfuncchunkname` / `_lua_getfuncchunkname`), and `ReplaceApis` swaps the engine's `lua_setfuncchunkname` and chunkname helper for the same-named LuaJIT exports. Their signatures live in the Lua-side signature DBs (`signatures_client/server.json`: offset 6304/6416 + pattern). Windows and Linux share the layout; macOS has no such guard. Also fixed dead code in `lua_getinfo_game`: the `@` strip was assigned to `ar->source` before `memcpy(ar,&iar,...)` overwrote it (`luajit/src/lj_debug.c`); it now patches `iar.source` with NULL / not-requested guards.

- Linux/macOS packages no longer fail on `render.shadow`, and the Lua plugin registry is now **discovered from disk**: `Mod/plugins/init.lua` no longer carries a hand-written package list — it calls the new `GameInjector.DS_LUAJIT_list_plugin_packages(plugins_dir)` export (`core/PluginPath.cpp::list_plugin_packages`; same filesystem the native loader scans, returns sorted `plugin_*` dirs that contain `modinfo.lua`, paths decoded as UTF-8). The Windows-only `plugin_render_shadow` is therefore never referenced on non-Windows packages, where its directory does not exist — previously `load_package` raised on the missing `modinfo.lua`, and `modmain` runs `plugins/init.lua` without `pcall`, so the whole AfterModMain registry aborted (every plugin dropped). Packages load one-by-one under `pcall` (a broken package is logged, the rest still register); without `GameInjector` (not injected / no `core.vm` / unit-test runs) the plugin system is fully disabled — `init.lua` returns an empty registry and logs why, with no static fallback list. `test_plugin_path` covers the discovery semantics.

- Every install entry point (`install.ps1`, `install.sh`, `Mod/install.bat`, `Mod/install_linux.sh`) now wipes <game>/data/unsafedata (stale Injector marker, boot log, plugin config) once the package is verified on disk and before the shell is deployed, so a marker left pointing at the previous install cannot cause "installed but no effect"; a failed delete only warns (`rd /S /Q` in `Mod/install.bat`, `rm -rf` in the shell scripts). The Lua-side `luajit_*.json` already moved to the save dir, so that folder now holds only injector state - but plugin-manager config/pins are reset with it. The self-checks no longer treat an absent marker as a failure: the shell writes it on the first boot, so after the cleanup it is always missing (`[CHECK] ... absent`); only a marker that exists but points at a vanished module still counts.

- Workshop layout is now "published name != loaded name": `tools/update_workshop_tags.py --push-content` stages every module the game maps under `<name>.pkg` (`Injector.dll.pkg`, `deps/*.dll.pkg`, `plugins/<stem>/<stem>.dll.pkg`), and the runtime materializes the canonical name from it immediately before `LoadLibrary` (`core/PackagedModule.hpp`; entry points: shell `InjectorBootstrap` for module resolve + `deps/`, `DynamicPluginLoader` for package candidates, `CoreVmBootstrap` for `plugin_core_vm`). Steam updates a Workshop item by applying its file delta, and a mapped DLL can be neither overwritten nor deleted (`ERROR 5`) - as long as the canonical name sits in the item manifest, an update can never complete while the game runs and the whole mod stays on the old version. `.pkg` files are never mapped, so Steam can replace them at any time; the canonical file is refreshed on boot by PE build stamp (`TimeDateStamp` + `SizeOfImage`), and one already mapped by another process is kept (same version skew as before). A canonical derivative left behind by a package member the item stopped shipping is dropped only inside a packaged tree (no `.pkg` twin), so a developer build in a source tree is never deleted. Release packaging follows the same layout: `.github/workflows/release.yaml` (Windows leg) runs `tools/pack_payload.py Mod` right before zipping, so `windows_Mod.zip` also ships `<name>.pkg` only (`install.ps1` accepts either name in its self-check; **`cmake --install` never renames** - only the packaging tool `tools/pack_payload.py` does, at packaging time, with the same rule the workshop push uses, so a build-tree `cmake --install Mod/` stays a normal dev tree and the materializer is a no-op there). Linux/macOS need none of this: POSIX allows `rename()` over a mapped file (verified: the holding process still sees the old version, a new process sees the new one), while an in-place truncating write is what kills it (verified: mapped pages zeroed, `SIGILL`) - every writer in this repo renames first. Concurrent boots are safe too: each process stages into its own `*.ds_materialize_tmp_<pid>_<n>` and publishes with a single atomic replace (Windows `MoveFileEx(REPLACE_EXISTING)`, POSIX `rename`), so the loser of the race exits cleanly and a canonical already mapped by a peer stays untouched; a twin caught mid-rewrite by an item update is re-read and PE-section-checked, never published half-written. `update_pending` moves and `plugin.manager` installs use the same atomic replace and no longer fall back to in-place truncation (measured: 6 processes x 400 concurrent materialize + `LoadLibrary`, zero failures).

- Crash sentinel and `luajit_config.json` now follow Klei's mod io sandbox: since 759671 Lua only accepts a relative `unsafedata/...`, resolved under the **save directory** (`.../<steamid>/client_save/unsafedata`), while absolute paths and `../` fail with `invalid filepath`. The injector used to read/write `<game>/data/unsafedata`, so one logical file lived in two places - the mod's clear never hit the sentinel, `skip inject, find crash content` fired on every later boot, injection stayed off, `GameInjector` was nil and users only saw "mod not installed". Both sides now share one root: native resolves `GetClientSaveDir()` (`util/Unsafedata.hpp`; falls back to the most recently written `*/client_save` when the Steam id is unknown) and the mod keeps the relative `unsafedata/...`. `check_crash` moved after `sdk::steam::Initialize` (the sentinel needs the account id) and the directory is created as injection starts. Shell-owned files (marker, `ds_luajit_boot.log`) stay under `<game>/data/unsafedata` - they are written before the game's main and are unaffected by the sandbox. No compatibility with the old location: a leftover `<game>/data/unsafedata/luajit_config.json` is ignored. The sentinel also skips exactly one boot now (`{1}` -> `{2}`, the next launch injects as usual), a stock boot no longer wipes the record, the always-false `is_crash()` was fixed and the retry dialog works again.

- Linux dedicated server boot: fixed `nucleus_analyze_file(lua51) failed: nucleus load_binary failed: .../deps/liblua51.so` followed by an immediate process exit. The build image has no `binutils-dev`, so `3rd/nucleus` compiled `NUCLEUS_LOADER_NO_BFD` into `libfunction_relocation.so` (the package ships neither `libbfd-2.42-system.so` nor any BFD symbol) and Linux `load_binary()` fell through to the "no binary loader available for non-raw type" stub. Linux no longer depends on libbfd: `loader.cc` now has a native ELF64 loader (sections from `SHF_EXECINSTR` / `SHF_ALLOC` and not `SHT_NOBITS`, `STT_FUNC` symbols from `.symtab`/`.dynsym`, `.eh_frame_hdr` FDE seeds as before). The resulting FunctionTable matches the BFD path entry for entry on `liblua51.so`, `liblua51DS.so`, `liblua51Original.so`, `dontstarve_dedicated_server_nullrenderer_x64` and `dontstarve_steam_x64` (25324 / 27236 spans identical for the two game executables). macOS still uses BFD.

- Linux boot: `libfrida-gum.so` is now linked with `-Wl,-z,noexecstack` (`tools/setup_frida_gum.py`). glibc >= 2.41 refuses to `dlopen` a DSO that requires an executable stack (`cannot enable executable stack as shared object requires`), and the shell loads the real Injector with `dlopen`, so Ubuntu 25.04+/WSL2 failed at boot (#45/#47).

- Injection diagnostics: `nucleus_analyze_file` failures now carry the loader's own reason (`nucleus load_binary failed: <path> (<loader reason>)`, likewise for disasm/CFG) instead of the bare wrapper string.

- On Windows, `lua51DS`/`lua51DS_gengc` can publish LuaJIT trace symbols through the Microsoft-JScript ETW provider (`57277741-3638-4a4b-bdba-0ac6e45da56c`) - no manifest install, no JIT PDB. The publisher is **off by default at runtime** and switched process-wide from Lua with `require("jit.profile").etw(true|false)` (query with `etw()`): `etw(true)` also flushes that VM's traces (equivalent to `jit.flush`, so every live trace ends up with a record and no stale identity survives) and `etw(false)` reports MethodUnload/SourceUnload/ScriptContextUnload at once and stops publishing, with the records freed by their owning VM instead of another thread. **A game or host must therefore call `etw(true)` in the injected VM** (the integration tests and `--hold-for-profile` do), otherwise the ETL carries no JIT names. Once on: every committed trace publishes one source and one method record, so `CPU Usage (Sampled)` in WPA/PerfView resolves a sampled PC inside `[T->mcode, T->mcode + T->szmcode)` to `LuaJIT::TRACE_<traceno>::<chunk>:<startline>`. `tests/performance/cpu.wprp` subscribes it with keyword `0x3` (runtime load/unload plus the start rundown), so attaching to a process that already compiled traces still resolves them, and its event collector buffers were raised because the GUID is shared with every Chakra host on the machine (Edge/WebView2 emit tens of thousands of their own JIT events). The symbol name is the trace's starting line; exit stubs and the interpreter dispatch path are not covered, and `RtlAddFunctionTable` is deliberately not called (`lj_err.c` identifies JIT frames by the absence of a `RUNTIME_FUNCTION`), so native unwinding across JIT frames is unchanged. The chunk part comes from the Lua side: `@`/`=` prefixes are stripped, bare paths are kept (`scripts/xxx.lua`, as the DST engine passes them, so game traces read `LuaJIT::TRACE_12::scripts/worldgen_main.lua:243`), and names that look like source text (newlines or over 512 bytes) collapse to `(string)`. Publishing never holds the symbol-cache lock across an `EventWrite` (the lock only covers list/flag updates: ~0.2 us per committed trace, ~15 ns per record), and the worker is joined outside the lifecycle lock with a 5 s timeout diagnostic, so a backpressured session cannot stall trace compilation or VM create/close. `--jit-diagnostics`/`analyze.py` remain a separate stdout/`jit.attach` path, not an ETW symbol consumer. It is **not compiled by default**: opt in with `-DLUAJIT_ENABLE_ETW=ON` (CMake) or `XCFLAGS+=-DLUAJIT_ENABLE_ETW` (Makefile); `-DLUAJIT_TEST_ETW=ON` (together with `LUAJIT_ENABLE_ETW=ON`) builds the real-ETW integration tests for both GC variants (`luajit_<variant>_etw_symbols`; exit code 77 = CTest SKIP when the shell has no sampling privilege, a missing event fails, and `--hold-for-profile` supports the live mid-session attach check).

- `install.bat` / `install_linux.sh` are shell-only now: on Windows it copies the packaged `bin64\windows\Winmm.dll` into game `bin64` (skipped when already identical), on Linux it puts the packaged `bin64/linux/lib64/libInjector.so` into game `bin64/lib64` and rewrites the `LD_PRELOAD` launchers (real binaries kept as `*_1`, re-runs skip); both no longer migrate or delete mod files, write the marker, or prune stale game-dir DLLs. The old scripts did not converge on in-place updates - `if exist Injector.dll` / `[ -f libInjector.so ]` kept the previous version's Injector at the mod root and robocopy (no `/MIR`) / `cp -a` kept deps/plugins the new package had dropped, pairing a new shell with an old Injector, which is a boot-crash source. Source/destination are derived from the script's own location (caller cwd independent), Windows error messages no longer break cmd parsing through `(`/`)` in absolute paths, and `uninstall` only removes the shell plus the legacy marker (on Linux it also renames the `*_1` originals back).

- `dev_init.sh` / `dev_init.bat` (`tools/update_steam_paths.py`) now complete one more init step: after locating the game dir they write `<game>/bin64/steam_appid.txt` with the app id (default `322330`), so the manual creation described in the debug docs is no longer needed.

- One-line install: `install.ps1` (Windows, `irm ... | iex`) and `install.sh` (Linux, `curl ... | sh`) - pick the newest release/preview (`DSJ_CHANNEL` / `--channel`), locate the game root through Steam using the same rules as `tools/steam_env.py` (registry / `libraryfolders.vdf` / `appmanifest_322330.acf`, overridable with `DSJ_GAME_DIR` / `--game-dir`), stage the package and run the packaged installer (shell deploy; on Linux the marker and self-check as well).

- `install.ps1` now prefers the Workshop folder: when the game's library has `steamapps\workshop\content\322330`, the package is staged into `...\322330\3444078585` (the folder subscribers actually load, and the one `install.bat`'s `workshop\content\322330` branch maps back to `common\Don't Starve Together\bin64` in the same library); only without it does it fall back to `<game>/mods/<folder>`. `DSJ_MOD_FOLDER` / `-ModFolder` therefore only apply to the fallback. An existing target that does not look like this mod (no `modinfo.lua`) is still refused rather than overwritten.

- `install.ps1` asks before force-closing anything: when `dontstarve_steam_x64` / `dontstarve_dedicated_server_nullrenderer_x64` are still running (they keep the mod's DLLs mapped, so `Remove-Item`/`Copy-Item` would hit sharing violations), it prints the process names and pids and proceeds only on `y`/`yes`, then waits until they are really gone; any other answer - or a non-interactive host where `Read-Host` fails - aborts the install. The prompt happens before the download/unpack/delete/copy, so an abort leaves the disk untouched and costs no download. This closes the old order hole where the mod files were replaced first and `install.bat` killed the game unconditionally afterwards. Unattended runs can pass `-AllowKill` (or `$env:DSJ_ALLOW_KILL=1`) to skip the prompt and force-close directly.

- `install.ps1` output is localised: the Windows display language (`CultureInfo.CurrentUICulture`) selects Chinese or English, every log/warning/error goes through one message table (`Msg '<key>'`) and an unknown key prints as itself so gaps are visible. The Chinese strings live in the new repo-root `install.zh.json` (UTF-8 JSON, same keys as the English table); the script itself stays **pure ASCII without a BOM** - PowerShell 5.1 parses a BOM-less `.ps1` as ANSI (CJK turns into mojibake and breaks the parse) while `irm | iex` fails on BOM-prefixed text (`Windows` is not recognized as a cmdlet...), so the two encodings are mutually exclusive and CJK cannot live in the script. A missing table (offline / not yet published) or incomplete keys silently falls back to English.

- Inject diagnostics: the shell (Winmm / InjectorStub) now writes the resolve source, module path, load/export results and its own outcome to `<game>/data/unsafedata/ds_luajit_boot.log` on every boot (stderr kept); `install_linux.sh` finishes with a `[CHECK]` summary (shell / real module / `ldd`) and gained `install_linux.sh selftest` (a one-process live probe of the stub -> real-module chain); the script now re-execs under bash when started via `sh` (dash) instead of dying with a syntax error and doing nothing.

- `plugin.manager`: added a cross-process plugin-tree lock (`plugins/.ds_plugin_update.lock`, `LockFileEx`/`flock`) - the boot update check and installs serialize on it, so a client + Master/Caves boot wave performs a single check and never writes the tree concurrently (unsupported locking falls back to the previous unlocked behaviour with a note; the lock file is stamped with the holder pid/host for diagnostics). The boot check is now part of `plugin_manager` (the separate `plugin.autoupdate` module and its three dedicated services are gone), the manager mutex is no longer held across checks or applies so `status_json` keeps answering, and a waiting apply rebuilds its plan under the lock after at most 30 s instead of re-downloading what another process just installed.

- Install layout is package-only: only `plugins/<stem>/<stem>.<ext>` is accepted (manifest slots carry `package=<stem>`, `module` must be `<package><ext>`, `files[]` are package-relative so nested members such as `modinfo.lua` and `scripts/*.lua` finally install); flat modules are no longer candidates (the loader ignores and warns, manifest validation and zip extraction were tightened); when a member is locked the whole package moves to `update_pending/<package>/` so a new Lua face never pairs with an old module.

- Manifest platform slots and packaged meta now carry a `build_config` build stamp: assets of an incompatible class (MSVC Debug vs the Release family) are refused before any download.

- Tooling/tests: cross-platform pre-push ctest gate (`.githooks/pre-push` + `tools/pre_push.py`, skippable via `git push --no-verify` / `PRE_PUSH_SKIP`); game-launching ctests share a `RESOURCE_LOCK(dst_game_server)` so `ctest -j` no longer collides on the fixed ports (10999/8766/27016); the Injector resolves/scans only the current layout (the real module in the mod root) - `bin64`/`lib64` legacy candidates and deps search fallbacks were dropped.

- Tooling/tests: fixed the phantom timeouts of the game ctests on a Chinese Windows code page (`plugin_dedicated_sim_pause` / `plugin_client_inject_smoke` / `plugin_client_host_smoke` / `game_mod_throw_abort`). The harness decoded child stdout as UTF-8 with `errors="replace"`; the resulting U+FFFD cannot be encoded by a GBK console, so the reader thread died with `UnicodeEncodeError` and stopped draining the pipe - the game then blocked writing to stdout until the test timed out. `harness.logs.safe_print` now degrades on encoding failure, and the three runner entry points set stdout/stderr to `errors="replace"`, so the reader thread can no longer die on a print failure.

- Tooling/tests: fixed the Windows loader failures in the `plugin_hash_zip` / `plugin_apply_offline` ctests (`0xc0000135` for `jvm.dll`, `0xc0000139` for entry point `zip_file_add`). Both statically import vcpkg's `zip.dll`, which was not deployed next to the test binaries, so the loader followed PATH and picked a JDK's `bin\zip.dll` - a JNI library that imports `jvm.dll` and does not export the libzip symbols. The build now copies `zip.dll` plus its `bz2d/zlibd1` deps (`bz2/zlib1` in Release) next to each test executable, independent of PATH.

- Fixed the `dump_lua_mods` chunk routing (engine `lua_load` hook): a chunkname is not always a file path - `loadstring`/buffer loads pass the code itself as the chunkname (the modoverrides table, the save-data wrapper, the `GameLuaInjector.forceEnableLuaMod(...)` injected block all take that path). Those previously hit `find("../mods/")` + `npos + strlen` out-of-range slicing (a code block shorter than 8 bytes threw `std::out_of_range`) and the bogus `!exists()` test, while the thunk fallback was shadowed by an inner `auto output_path` and never took effect - dumps silently failed or landed under an illegal file name. `ChunkDumpPath()` now maps only `../mods/<mod>/<file>` (optional `@` prefix, no illegal path characters, <= 255 chars) to `dumped_lua_mods/<file>` and sends everything else to `dumped_lua_mods/thunk.lua` (write policy is covered by the next entry; a warning is emitted when the file cannot be opened). Verified on a dedicated server with `lua_vm_type=game`: `plugin_lg_probe/modmain.lua` lands as a real file while the modoverrides / save-data code blocks land in thunk.lua.

- Fixed `dump_lua_mods` producing only the tail of encrypted-mod sources (hercules / MyxlHttps family, e.g. workshop-3014076942): their loader feeds the decrypted source to the reader in ~8-byte slices **inside a single `lua_load`** (e.g. `myxl_date.lua` 245 slices = 1960 bytes, `speech_moyuxuanli.lua` 43k slices = 344112 bytes) and **re-enters `lua_load` while that reader is still draining**; the shared `thread_local LuaReaderWrapper` was cleared by those re-entrant calls, so every accumulated slice but the last was dropped and the dump held a few trailing bytes. Each `lua_load` now gets its own wrapper (re-entrant calls build and dump their own), so the whole file is assembled into one write: the files above now dump as complete plaintext sources (344112 / 70920 / 36360 / 1960 bytes). The write policy is also three-state now: slices of a stream are appended, a payload at least as large as the dump replaces it (a complete chunk), and stray small payloads after a complete dump are skipped (the complete 80154-byte modmain is no longer clobbered by the 652-slice re-stream that follows it). Dumps are written in binary mode (text mode turned `\n` into `\r\n`, so dumps did not match the real source).

- Tooling/tests: `game_mod_throw_abort` now matches the current game's mod-load failure behaviour - after a modmain error the engine no longer exits; it disables the mod (`Disabling <mod> because it had an error.`) and keeps starting/retrying. The test still requires the `[ds_harness] THROW_ABORT` print (force-enable reached the fixture), the nil-index error text, and the error being handled (disable line, or the engine-VM `Error loading main.lua`), but no longer requires the process to exit; `DedicatedProc.wait_exit` is removed with it.
