# World generation hotspot investigation, October 14, 2026

The dominant difference in the current Release worldgen workload is the
game-to-LuaJIT C API hook path. Ocean tile scans repeatedly hit ordinary Gum
interceptor thunks. Parsing does not explain the approximately five-second
map-generation gap.

## Workload and evidence

- Embedded game Lua 5.1 versus local LuaJIT, JIT explicitly off during Generate.
- Same Release injector/plugins and assertion/API-check-free Release VM as the
  [baseline](2026-10-14-release.md); VM revision
  `deaa4ed76fbd099db4002d8e2c0a44d853e71cc3`.
- LuaJIT DLL SHA256:
  `f84c2734477250325a9b171f0fd72d9fe5bb0aec8f599462c604fc9546c10fdf`.
- Seed 123456, SURVIVAL_TOGETHER, `world_size=default` (the game's Large setting,
  initial generator extent 425 x 425), isolated fresh saves/processes.
- All diagnostic maps succeeded on their first attempt.
- Normal JIT-off baseline: game 2.449276 s, LuaJIT 7.666627 s map wall medians.
- Four pairs with both diagnostic samplers: game 2.480-2.526 s,
  LuaJIT 7.801-7.956 s. The middle two pairs reverse VM order.

Square fill alone accounts for about 57% of the net difference. The earlier
native story/layout work is slightly faster with LuaJIT in this pair.
These are intervals between existing log markers; the final row includes
remaining generation work and must not be attributed to void outlining alone.

In `data/scripts/map/ocean_gen.lua`, `do_squarefill` (lines 210-221) scans the
map and checks neighboring tiles with `IsCloseToImpassable`/`IsCloseToWater`.
`squareFill` (149-160) repeatedly calls GetTile/SetTile inside nested loops.
`AddShoreline` (412-425) repeats similar tile and neighborhood queries.
Lua sample stacks identify these functions by name and line.

Uncached outermost require intervals total 0.132419 s in the game VM and
0.095396 s in LuaJIT. These include loading, parsing and executing modules,
so they are an upper bound on parsing in the measured Generate interval.
They exclude modules loaded before Generate and are not a parser-only benchmark.
The final LuaJIT sampler reported C 90.27%, interpreter 9.39%, GC 0.34%
of 1470 samples. C state by itself does not identify native functions; the
external PC snapshots establish the interception hotspot.

## Native interception evidence

The final WorldSim capture has 512 LuaJIT-group snapshots:

- 46.88% outside loaded modules, almost entirely the shared Gum thunk page.
- 25.78% inside frida-gum.dll.
- 12.70% inside lua51DS.dll.
- 9.96% inside the game executable.

Within Square fill, 205 of 235 snapshots (87.23%) are in generated code or
frida-gum.dll. In the embedded-game group there are no Gum/dynamic-code samples
in this capture. Similar module distributions recur in the other three pairs.

Captured dynamic bytes decode to Gum's ordinary enter/leave thunks. Dominant
PC offsets are 0x55, 0xa9, 0x155 and 0x19b, immediately following FXSAVE or
FXRSTOR. The thunks call frida-gum.dll RVAs 0xdbc8 and 0xdf5c, matching
`_gum_function_context_begin_invocation` and
`_gum_function_context_end_invocation` by their implementation and emitted code.
Gum additionally maintains thread-local invocation stacks and listener state.
PCs after an instruction are reported as observed; their counts are not a
cycle-accurate measure of the preceding instruction alone.

Observed R12/RDI context candidates were checked against the existing server
Lua API signature database and the unique `luaModuleSignature` anchor.
The Lua block is at game RVA 0x483660 for the recorded server executable.
Validated contexts include `lua_tointeger`, `lua_touserdata`, `lua_remove`
and `lua_settable`. All have interceptor type byte 0 (DEFAULT) and replacement
addresses in the Release LuaJIT DLL. Their replacement exports match their
API names. This identifies actual ordinary API replacements, rather than
merely assuming every anonymous executable address belongs to Gum.

## Why fast replacement falls back

`GameLuaContextImpl::ReplaceApis` first calls `replace_fast`, then falls back
to ordinary `replace` when the fast attempt fails.

The staged Gum x64 backend reserves a worst-case 16-byte redirect for FAST.
DEFAULT can allocate a nearby trampoline and use a 5-byte redirect.
Its online relocation checker stops at a CALL instruction.

The verified game `lua_tointeger` (RVA 0x483d00) and `lua_touserdata`
(0x483ec0) entries start with a 4-byte stack adjustment followed by a
5-byte call to index2adr. The checker therefore reports only 9 relocatable
bytes, which fails the FAST requirement but satisfies a nearby DEFAULT
redirect. The resulting heavy enter/leave path is repeated for tile queries.
This is supported by both source and captured DEFAULT hook contexts.

The current Release frida-gum.dll's exported relocation checker was also
called directly on the verified lua_tointeger entry bytes, without executing
or patching those bytes:

| Scenario | Required bytes | Result | Reported relocatable bytes |
| --- | ---: | --- | ---: |
| Online | 5 | Success | 9 |
| Online | 16 | Failure | 9 |
| Offline | 16 | Success | 20 |

This confirms the online limitation in the exact staged DLL, rather than
assuming the local Gum source and binary agree. The offline result alone does
not establish that changing the injection lifecycle to offline relocation is
safe; a nearby direct relay is another possible implementation direction.

Relevant local source:

- `src/DontStarveInjector/plugins/plugin_core_vm/game/GameLuaContextImpl.hpp`,
  ReplaceApis fast attempt and normal fallback.
- `3rd/frida-gum-src/gum/backend-x86/guminterceptor-x86.c`,
  prepare_trampoline and enter/leave prologs/epilogs.
- `3rd/frida-gum-src/gum/arch-x86/gumx86relocator.c`,
  gum_x86_relocator_can_relocate online CALL stop.
- `3rd/frida-gum-src/gum/guminterceptor.c`,
  begin/end invocation implementation.

The next performance experiment should remove the ordinary interceptor path
for these high-frequency API replacements, such as through a nearby direct
relay. This investigation does not alter native hooks or VM/tailcall code,
and does not measure performance after removing the interception overhead.
It cannot quantify the residual interpreter or compatibility cost.

## Reproduce and limitations

Run with `--sample-lua --sample-native` as described in the profile README.
Analyze the final capture with:

```powershell
python tests/performance/analyze.py builds/game-performance-20261014-hotspots-final `
  --disassemble `
  --signatures builds/game-performance-runtime-release/src/DontStarveInjector/Release/signatures_server.json `
  --game-lua-base-rva 0x483660
```

ETW CPU capture failed with 0xc5585011 because the token lacks administrator
profiling privileges; WPR was confirmed idle afterward. The fallback captures
wall-time thread snapshots, not ETW CPU samples. Requested sampling interval
is 5 ms but observed Windows spacing in these runs is approximately 15.5 ms.
Total Suspend/GetContext/Resume call time was 0.033642 s for the final LuaJIT
capture and 0.010009 s for the game VM; cache and scheduling perturbation add
unmeasured overhead. Lua sampling/logging also alters timings.

VM state samples are asynchronous and C-call samples can coalesce at safe
points. Fixed seed does not guarantee identical maps across VMs with different
random-number or iteration semantics. The repeated phase/module results support
the large hotspot; they do not establish precise API call counts or tiny speedups.
Original Winmm/config SHA256 values matched after all runs.
