# Embedded game VM baseline: 2026-10-14

This baseline compares the installed game's embedded Lua 5.1 (`lua_vm_type=game`)
with the local LuaJIT fork. Both groups use the same Release injector, plugins,
shell and measurement probes. It measures the embedded VM with the injector
present, rather than an untouched game installation.

## Environment and builds

- Host: AMD Ryzen 9 7945HX, 16 cores / 32 logical processors.
- Platform: `Windows-10-10.0.26200-SP0`.
- Game version reported in the server log: `756039`.
- Repository HEAD: `75a4429ed3578e9b40ee107a22d891031b68757d`.
- LuaJIT HEAD: `deaa4ed76fbd099db4002d8e2c0a44d853e71cc3`, clean source tree.
- LuaJIT configuration: Release, MSVC `/O2 /Ob2 /DNDEBUG /MD`.
- `LUA_USE_ASSERT`, `LUA_USE_APICHECK`, RETM/OOM diagnostics and sanitizers: disabled.
- Injector, plugins and Windows Winmm shell: Release.
- World settings: offline Master, `SURVIVAL_TOGETHER`, default world size, seed `123456`.
  In this installed game version, `default` is the UI's Large setting, with an
  initial generator size of 425 x 425. Huge uses 450 x 450. These are inputs to
  `WorldSim:SetWorldSize`; the generator can subsequently adjust dimensions.

  each measured map-generation call. The embedded VM records `jit=false`;
  LuaJIT records `jit=true` at map entry. The JIT-off follow-up disables JIT.
- Warmups are excluded, and sample order alternates between game/LuaJIT and

## Interpretation

This workload shows a large map-generation difference and a smaller overall
startup difference. These measurements do not isolate the cost of tailcall
compatibility or RETM stitching.

Client startup differs by about 1.9% in these two pairs. This small sample count
does not establish a reliable client speedup. The total startup workflow is
about 10.4% slower with this LuaJIT build, and including hold/teardown reduces
the observed difference to about 6.8%.

Map wall time and process CPU time are sampled externally at stdout boundaries,
including log delivery delay and native generator work. Fixed seed and settings
do not establish identical generated output across VMs with different random
or table-iteration semantics. Filesystem caches and host load are uncontrolled.
Warmup captures slow first-process initialization and is excluded from summaries.
Every sample creates a fresh process and VM, so warmup does not preserve JIT
traces for measured samples. The measurements include the first generation's
compilation cost when compilation occurs.
Client readiness denotes the existing smoke test's world-loaded milestone,
rather than the first rendered frame or a playable character.

Earlier assertion/API-check builds and attempts with mixed Debug modules are
superseded and are not part of this baseline.
