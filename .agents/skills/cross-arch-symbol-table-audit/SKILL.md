# Auditing an already-applied symbol table (no pipeline re-run)

Use when a symbol set was written by a multi-stage matcher and some stages turn out to be unreliable. Re-running is usually the wrong move: the stages have fixed precision, so they re-derive the same errors; and later stages overwrite earlier pairings, so the TSV history is not a record of what is in the program.

## 1. Establish the authority

Every applied name must carry a plate comment written at apply time, e.g.
`cross-arch: high | callers A=0x9643c0 score=0.786 callers=11 proxy=0`.

Export it (Ghidra script `DstExportProvenance`): iterate all functions, read the
PLATE comment, keep rows containing `cross-arch:`; write `va \t comment`.

If a stage does not write provenance, fix the writer first — otherwise the table
cannot be audited later.

## 2. Test each claim against its own evidence class

| method | pass rule |
|---|---|
| `bind` | native binding name equal on both sides (fixed extraction) |
| `string` / `jaccard` | shares a literal rare on both sides, or string-set Jaccard >= 0.5 |
| `score` / `propagate` / `callers` | needs an *independent root*: rare shared literal, or instruction-count ratio >= 0.9 |
| `vtable` | address still produced by the current vtable pass |
| `review … same` | manual verdict, skip |
| no `A=` in the note | not auditable; report, never auto-clear |

Pair resolution: use the `A=0x…` in the comment. Never build it from history TSVs
with later-wins semantics — a stale file generated by a buggy extractor will
silently replace correct pairings.

## 3. Clear, then prove nothing depended on it

1. dry-run the clear (`DstClearNames <tsv> dry`), expect `missing=0`;
2. apply;
3. re-export names and re-run every downstream consumer (vtable anchors,
   propagation seeds) and diff: identical table/name counts mean none of the
   cleared names was load-bearing. If a count drops, the dependent output must be
   re-derived and re-applied.

Keep the cleared list on disk (`audit_clear.tsv`): it is the only route back for
manually reviewing the ~half that were probably right.

## 4. Reporting

State, per provenance class, how many claims pass and how many do not, the
expected precision of the failing class (measured on a holdout, not guessed), the
coverage before/after, and the cost (which correct names were lost). A coverage
drop with unchanged validated classes is a quality gain, not a regression.

## Pitfalls

- Comment API: `Listing.getComment(CommentType.PLATE, …)` may not exist; fall
  back to `Function.getComment()`.
- vtable applies often write `cross-arch: vtable | A=0x…` with no method word —
  treat a method token starting with `A=` as the tier name.
- 20–30% of names typically have no `A=` (legacy apply format, manual edits);
  never clear them on the basis of a failed re-derivation.
