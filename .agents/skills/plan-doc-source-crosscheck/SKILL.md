# 目的

审查一份针对已有代码库的技术实施计划（RFC/PLAN 文档），输出「有源码证据、有严重级、有最小修订」的问题清单，并把修订落回计划文档。不实现计划本身。

适用触发：用户说「review 此计划」「更新一下文档」；计划涉及并发/ABI/注册生命周期/构建链接这类易失真内容。

# 1. 先划定审查边界

- 明确交付物：只改计划文档（+ 一份本地审查记录），不动实现文件，不声明验收已通过。
- 把「缺少实现」本身排除：计划阶段没有代码是正常的，只报计划自身自相矛盾、与源码事实冲突、或验收无法暴露目标失败。
- 计划文档里的每个「已核实」条目都要重新取证；行号引用会漂移。

# 2. 切片并行核对

按计划的自然分段切开（编码/发布生命周期、生成器帧状态、运行时桩、构建与验收），每片一个只读 subagent，要求：

- 引用 `文件:行号`，给出可失败场景（哪条验收会静默通过/静默失败）；
- 明确区分「既有代码限制」与「本计划引入的缺陷」；
- 自带「已排除的候选」清单，防止父 agent 重新争论。

父 agent 同时自己核对最关键的交叉点（跨片的接口契约），因为 subagent 只看到自己那一片。

# 3. 只接受可判定的证据

每条发现必须能回答：

1. 计划第几行？2. 源码哪行反驳/支持？3. 什么运行时或链接场景会暴露？4. 最小修订是什么？

排除：无来源的编码推断（例如 CIE 指针符号方向，未经源码确认不要写进发现）、措辞偏好、以及「计划没逐个列出调用点」这种可被验收自动发现的完整性诉求。

# 4. 严重级与修订形态

- P0/P1：默认配置下必然失败的路径；P2：验收无法覆盖、或只在非默认配置触发；P3：配置边界应写明。
- 修订优先写成对计划条款的**限定语**（适用范围 + 不覆盖什么），而不是要求扩大实现范围。审查的价值在于缩小承诺，不在于增加工作量。
- 反复检查「审查本身有没有偷偷扩大任务」：例如把局部保证写成全链路保证，就会逼出无关重构。

# 5. 落回文档

- 逐条 `edit` 到对应段落；同一事实只在一处定义（正文条款），验收段只引用不复述。
- 验收矩阵新增的每一行必须是可执行、可判定的（强制构造边界条件，而不是「跑一遍看是否通过」）。
- 执行路线（脚本块）必须真的覆盖计划承诺的每条交付路径；只跑主构建系统会漏掉另一套构建的链接契约。
- 完成后回读改动区间与相邻章节，确认无重复、无悬空引用、无与「完成标准」冲突。

# 6. 常见失真点（直接对照）

- **平台分支**：计划描述的尾声/序言顺序只对默认 ABI 成立；未启用的宏分支往往是死代码且自身有 bug，不要为它扩大任务。
- **尾跳 vs 调用**：改「wrapper 进入方式」是协议变更，不能写成「保留现有布局」。
- **链接依赖**：把库加进全局变量 ≠ 共享库产生 `DT_NEEDED`；`-shared` 允许未定义符号，构建绿灯不代表宿主能加载。
- **掩盖分支的默认值**：大块地址预留、近地址假设、固定容量上限都会让边界代码在测试里不可达。
- **反注册可观测性**：返回 void 的注册 API 无法判定成功，只能靠顺序（先注销后释放）与副作用检查。
- **校验器与约定冲突**：新增「空数据表示默认规则」时，要检查共享校验函数是否把空数据判为错误。

# 7. 交付

简短列出：默认配置是否有阻断 → 每条的「计划位置 / 源码依据 / 修订」。明确写出未做哪些验证（未构建、未跑功能测试），不要用源码审查暗示已通过。
